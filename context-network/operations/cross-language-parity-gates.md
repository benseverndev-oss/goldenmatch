## Cross-language / native drift gates (2026-07-05)
- **`api_parity` gate** (`scripts/check_api_parity.py` + `parity/<pkg>.yaml`, 6-package matrix) partitions each package's operation surface into shared/python_only/ts_only and fails on undeclared Python↔TS drift. Surfaces gated: **MCP tools + CLI commands + `a2a_skills`** (A2A AgentCard skills, added #1461 for the 4 A2A packages goldenmatch/goldencheck/goldenflow/goldenpipe). A tool/command/skill add/rename/remove must be reflected in the manifest in the SAME PR. Emitters: `emit_python_surface.py` (box-safe) + `emit_ts_surface.mjs` (CI-only). The gate skips a surface a package lacks (infermap/goldenanalysis have no A2A). Adding a surface = one line in `SURFACES` (it already skips per-package-absent); gotcha: `a2a_skills` was the tests' unknown-surface fixture — repoint it. **`scorer_kernels` also has a COVERAGE FLOOR (`check_scorer_coverage`, goldenmatch + infermap):** every scorer in the `scorers` surface must be EITHER kernel-backed (in `scorer_kernels`) OR listed in a `scorer_kernels_deferred:` map (scorer → reason) — an uncovered/unclassified scorer FAILS, so a new scorer, or a kernel that regresses to a pure-language fallback, can't silently sit uncovered the way "5 of 19 kernel-backed" did. **(2026-07-25: infermap became the second package to model this — `parity/infermap.yaml` declares `scorers`/`scorer_kernels` from `infermap.scorers.SCORER_NAMES`/`SCORER_KERNELS` ↔ `core/scorers/registry.ts`, so its M:N scorers are gated too; alias is declared `declined` (trivial `strip().lower()` + runtime-DATA lookup, no meaningful kernel) and llm `n/a` (model-backed).)** `scorer_kernels_deferred` is a classification MAP not a partition surface (skipped in `check_structure`, shape-checked in `check_scorer_coverage`); each entry's reason is prefixed `deferred --` (will kernelize) / `declined --` (won't) / `n/a --` (not a string kernel). Removing a scorer's kernel without adding a deferral entry fails CI. **`blocking_strategies` also has a COVERAGE FLOOR (`check_blocking_coverage`, goldenmatch-only, added 2026-07-25):** every strategy in the `blocking_strategies` surface must be EITHER `shared` (implemented on both surfaces) OR listed in a `blocking_kernels_deferred:` map (strategy → reason) — a non-shared strategy with no deferral FAILS, so a python_only/ts_only blocking strategy is a documented decision not a silent gap. It's a lighter MANIFEST-MAP floor (not an emitted partition like `scorer_kernels`) because blocking is mostly group-by orchestration — only lsh/simhash/perceptual have a `-core` kernel, so there's no source-level "kernel set" to emit + compare. `blocking_kernels_deferred` is skipped in `check_structure` like `scorer_kernels_deferred`. (2026-07-25: `lsh`/`perceptual` were ported to TS — `buildLshBlocks`/`buildPerceptualBlocks` over the already-ported `sketch.ts`/`perceptualWasm` kernels, cross-language fixture `blocking-strategies.json` — so both moved python_only → shared; only `simhash` stays python_only, declined as model-backed.) **ADVISORY (non-gating) SQL surfaces `postgres` + `duckdb` (added 2026-07-25, goldenmatch-only):** the parity gate now ALSO reports the goldenmatch SQL function inventory for VISIBILITY — `scripts/emit_sql_surface.py` STATIC-parses the pgrx crate's `#[pg_extern]` fns + the `goldenmatch_duckdb` package's `create_function`/`CREATE MACRO` names (box-safe, no toolchain; siblings goldencheck_*/goldenflow_* + `_impl` helpers excluded), recorded in `parity/goldenmatch.yaml` as `{functions: [...]}` inventory blocks. `check_sql_advisory` reports DRIFT (source vs manifest inventory, robust) + a labeled HEURISTIC coverage count (Python MCP+CLI ops with a namespace-normalized SQL match) — but it NEVER affects the exit code (SQL delegates to the Python `score_strings`/`score-core` reference, so scorers can't drift; operation coverage is roadmap, not a per-PR gate). `check_structure` skips both like `scorer_kernels_deferred`. Refresh after adding/removing a SQL fn: `python3 scripts/emit_sql_surface.py goldenmatch` then sync the two lists. **`transforms` parity surface extended to goldenflow (2026-07-25):** `parity/goldenflow.yaml` now declares a `transforms` partition (the goldenflow analogue of goldenmatch's transforms surface — a partition, NO kernel floor; goldenflow-core kernel-backing is separately guarded by the `native_symbols` `literal` idiom gate) emitted from `goldenflow.transforms.list_transforms` (Python — all submodules register via `import goldenflow`) ↔ `core/transforms/registry.ts listTransforms()` (TS). 113 transforms are shared 1:1; the sole delta is TS-only `category_llm_correct` (edge-side LLM corrector, model-backed, declared `ts_only`). So a transform added on one language only now FAILS the gate. **`analyzers` parity surface added for goldenanalysis (2026-07-25):** a new `analyzers` entry in `SURFACES` + `parity/goldenanalysis.yaml`, emitted from `goldenanalysis.registry.available_analyzers` (Python) ↔ `core/registry.ts availableAnalyzers()` (TS) — 5 analyzers shared 1:1 (cluster.distribution/frame.summary/key.integrity/match.rates/quality.rollup), partition-only (no kernel floor; analyzer kernel-backing is guarded by native/wasm parity fixtures). (`key.integrity` was python_only in v1 — the semantic-layer key-integrity certificate projection — and ported PY→TS 2026-07-31 as `core/analyzers/keyIntegrity.ts`, a pure certificate projection like `match.rates` with no kernel, closing the last goldenanalysis analyzers gap.) (Net: the compute-parity discipline that began goldenmatch-only now spans goldenmatch scorers/blocking/transforms + infermap scorers + goldenflow transforms + goldenanalysis analyzers — every core package with a cross-language compute surface is now gated.)
- **`native_symbols` gate** (`scripts/check_native_symbols.py`, #1459, box-safe) reconciles host native-kernel references (`native_module().X` / `getattr`/`hasattr` across module-binding aliases `_nm`/`nm`/`mod`/`native_mod` bound to `native_module()`/`_ensure_native()`) against the kernel's `wrap_pyfunction!` exports in `native/src/lib.rs`. FAIL on referenced-but-not-registered (the silent-fallback #688 class); REPORT unwired exports. The alias resolution is load-bearing — a `native`-only scanner silently under-scans. **Rolled to 4 packages** (CI matrix): goldenmatch/goldencheck/goldenanalysis via the `runtime` idiom (`native_module().X`); **goldenflow via a `literal` idiom** — its kernel refs are quoted `*_arrow` string literals in the `transforms/_native.py` shim (`_kernel_runner("phone_e164_arrow")`), NOT attribute access, so the gate carries a per-package `idiom` (`runtime`|`literal`) + `literal_pattern`. **goldenpipe is intentionally NOT gated** — its `goldenpipe-native` is a reference-mode parity oracle (pure-Python planner is the runtime; kernel exists only for the planner parity gate #1424), no host-accelerated refs to reconcile. Also `_WRAP` now accepts BARE `wrap_pyfunction!(fn)` (analysis/pipe) + `mod::fn`.

- **GoldenAnalysis Wave 1b (WASM for the frame kernels) is CONSCIOUSLY DEFERRED** (`docs/superpowers/specs/2026-07-06-goldenanalysis-wave1b-deferred.md`). The frame kernels (`duplicate_row_ratio`/`distinct_count`/`null_ratio`) have NO clean WASM boundary — the Rust core takes interned `u64` columns, and the interning (`intern_column` + `canon_f64_bits`) is Arrow-specific, while TS operates on `FrameRows` with `JSON.stringify` keys. Browser frame-dedup isn't an established workload. Revisit ONLY on a real measured in-browser workload; then arrow-in-wasm is the thesis-pure path. Instead of the WASM build, we locked the TS↔Python **equality semantics** with an adversarial cross-surface fixture (`frame_kernels_adversarial.json` + `test_frame_kernels_parity.py`/`frameKernels.parity.test.ts`): `-0.0`/`0.0`, `NaN`/`NaN`/null, empty-vs-null, int-vs-float. **GOTCHA it caught:** TS `duplicateRowRatio`'s `rowKey` did one `JSON.stringify(cols.map(...))`, which serializes BOTH `NaN` and null to JSON `null` → conflated them → over-counted dups on any column mixing NaN+null (`1.0` vs Python `6/7`); TS's own `nUnique` already distinguished them. Fixed by keying each cell like `nUnique` (`aggregate.ts::rowKey`); NaN-free frames (incl. the `report_frame_summary` lock) are byte-unchanged. Frames are built in CODE both sides (JSON can't hold `NaN`/`-0.0`); the fixture holds only finite outputs.
