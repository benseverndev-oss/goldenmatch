## Post-fold GitHub Actions
Only `.github/workflows/` at the repo root runs. Workflow files left under `packages/python/<pkg>/.github/workflows/` from pre-fold repos are orphaned (silently ignored). v1.6.0 release shipped no PyPI publish until `publish-goldenmatch.yml` was added at the root.
- `publish-goldenmatch.yml` — fires on **push of a bare `v*` tag** (prefixed tags like `goldenmatch-js-v*` don't match `v*`); `workflow_dispatch` with a required `tag` input for retro-publish. Uses `PYPI_TOKEN` (trusted publishing not configured; the `attestations: true` input is therefore ignored — that published warning is benign). **Cut a release by pushing the tag ONLY — the workflow OWNS the GitHub Release; do NOT `gh release create` it yourself.** Notes are auto-extracted from the `## [<version>]` CHANGELOG section. **Immutable-releases lesson (v2.1.0, 2026-06-18):** the repo has GitHub's immutable-releases setting ON, which seals a release's assets at publish time — so the old "human publishes the release, CI attaches signed wheel/sdist/sigstore bundles afterward" flow fails (`Cannot upload asset ... to an immutable release`). The workflow now builds → PyPI publish → cosign-sign + attest → create a **draft** release with the assets attached → `gh release edit --draft=false` to publish (assets only attach while the release is a draft). v2.1.0 itself shipped to PyPI fine but its GitHub Release carries no attached sigstore bundles (the pre-fix red).
- **Cut a `v*` release from CI with `cut-goldenmatch-release.yml`** (`workflow_dispatch`, input `version` = the bare version, e.g. `3.5.0`). It validates the version against main (pyproject/`__init__`/server.json lockstep + tag-is-new), pushes the bare `v<version>` tag from the runner, then CALLS `publish-goldenmatch.yml` reusably (`workflow_call`) so the tag exists BEFORE publish — the final `gh release edit --draft=false` only flips the draft flag instead of creating the tag ref. Use this when you can't `git push` the tag yourself (the managed dev sandbox 403s on tag pushes). **Never `gh release create` a `v*` release by hand:** immutable-releases PERMANENTLY tombstones the tag name (`tag_name was used by an immutable release`), and deleting the release does NOT free it — the version can then never get a proper signed Release (the v3.5.0 incident; 3.5.0 shipped to PyPI + MCP fine but has no GitHub Release). Companion to `cut-native-release.yml`.
- `publish-mcp.yml` — auto-syncs `packages/python/<pkg>/server.json` to the official MCP Registry (`registry.modelcontextprotocol.io`) after every PyPI publish, THEN mirrors `server.json`'s `description` onto the matching Smithery listing (`server.json` is the single source of truth for the description on both surfaces). Same tag patterns as the per-package PyPI workflows. Registry auth via GitHub OIDC (`id-token: write`); no secret. The Smithery sync (`PATCH https://api.smithery.ai/servers/{namespace%2Fname}`, namespace `benzsevern`) needs a **`SMITHERY_API_KEY`** repo secret — absent it the step prints a notice and skips (never fails the publish); a not-yet-listed server (HTTP 404, e.g. infermap/goldenanalysis until added on the Smithery dashboard) also skips, any other non-2xx is a warning only. The MCP Registry is IMMUTABLE per version — re-publishing an already-listed version returns 400 `cannot publish duplicate version`, which the publish step swallows as benign (notice, not failure) so a `workflow_dispatch` refresh stays green; only a NEW version actually pushes to the registry. The Smithery sync step runs `if: ${{ !cancelled() }}` (independent of the publish outcome), so `workflow_dispatch` with `package` input (`all` / one of six) DOES force-refresh the Smithery description without re-tagging even though the registry side no-ops. Smithery LISTING creation/removal is still a manual dashboard action — this only keeps the description of an already-listed server in lockstep.

## Workflow trigger ordering
A push of a tag that points at a commit predating a workflow file's introduction will NOT fire that workflow — GitHub Actions reads the workflow definition from the tag's commit, not from main HEAD. After landing a new `publish-*.yml` at the root, either re-tag at HEAD-of-main once the workflow is committed, or use `gh workflow run <file> --ref main` (which reads the workflow from main and checks out via the `ref` input). Bit us on `goldenmatch-js-v0.4.0` (v0.4.0 merge predated the publish workflow) and on `v1.6.0` (Python orphan).

## Publish workflows: read version from git tag, not PyPI
`publish-mcp.yml` and the per-package `publish-<pkg>.yml` workflows both fire off `release: published`. If the MCP sync queries PyPI for the version, it races against the parallel PyPI publish and reads the prior version → registry returns 400 "cannot publish duplicate version". Always derive version from the git tag (`${TAG##*-v}`, then `${V#v}`) for release events and from `pyproject.toml` for `workflow_dispatch`. PR #167 has the canonical pattern.

## golden-suite lockstep: a member release drags golden-suite
**STANDING RULE:** whenever a package the `golden-suite` meta-package bundles (goldenmatch, goldencheck, goldenflow, goldenpipe, infermap/GoldenSchema, goldenanalysis, and the `*-native` accelerators) cuts a new PyPI release, **golden-suite must also move** — bump its floor for that member to the new version (`packages/python/golden-suite/pyproject.toml`) and cut a new golden-suite release. Why: golden-suite's `>=` floors *technically* auto-pick-up new members on a fresh install, but bumping the floor **mandates** the new baseline (matters when the member carries a real fix, e.g. the B1 silent Latin-1 corruption fix in goldenmatch 2.8.0) and keeps the advertised versions honest. Sequencing (critical): (1) land the member on PyPI FIRST — golden-suite's bumped floor must be SATISFIABLE on PyPI before it is tagged (the `>=2.6` unsatisfiable-floor trap); (2) branch golden-suite's bump OFF main only after the member's version bump merged, so the uv workspace carries the new member version (CI resolves golden-suite floors against the workspace, not PyPI); (3) bump `[project].version` + `golden_suite/__init__.py` `__version__` (the two lockstep spots; no server.json) + CHANGELOG, merge, then tag `golden-suite-v<x.y.z>` → `publish-golden-suite.yml` → PyPI. Deps-only meta-package, no code.

## MCP Registry `mcp-name:` README marker (PyPI ownership)
The registry proves PyPI ownership by requiring an `<!-- mcp-name: io.github.benseverndev-oss/<pkg> -->` marker in the package's PyPI long-description (the README). It must be the FIRST line. All published suite packages carry it; a package missing it fails `mcp-publisher publish` with HTTP 400 `ownership validation failed`. Because PyPI releases are immutable, adding the marker only takes effect on the NEXT PyPI release — you cannot retro-fix an already-published version. When scaffolding a new suite MCP package, add the marker to its README at creation time. (Bit goldenanalysis: 0.1.0 shipped without it and it was the one suite server missing from the registry; 0.2.0 carried the marker and it has been listed since.)

- `publish-containers.yml` builds 7 images. 6 are new (created by this monorepo's GITHUB_TOKEN, default permissions). `goldenmatch-extensions` pre-existed from the standalone repo — its "Manage Actions access" must explicitly grant `benseverndev-oss/goldenmatch` write role, or pushes fail with `permission_denied: write_package`.

## publish-containers flakes
- A red `publish-containers` on `main` is almost always a transient registry timeout, NOT a code bug (audited: 11 fails / 30 days, across 6 different packages). Dominant cause: `docker/setup-buildx-action` bootstraps BuildKit by pulling `moby/buildkit:buildx-stable-1` from Docker Hub anonymously; 7 matrix legs pulling in parallel on every main push intermittently time out (`context deadline exceeded`) under Docker Hub's shared-runner-IP throttling. Secondary: transient ghcr 502s and GHA-cache (`actions-cache` blob) copy errors at `Build and push`.
- Fix (PR #846): a `mirror` job republishes buildkit + binfmt into `ghcr.io/<owner>/{buildkit,binfmt}` once per run (retried), and the legs pull those helper images from ghcr via `setup-qemu` `image:` / `setup-buildx` `driver-opts:` (ghcr login moved AHEAD of the buildx bootstrap so the private mirror is pullable). Native retry-once twins (`continue-on-error` + `outcome == 'failure'` guard, no third-party action) on QEMU / Buildx / Build-and-push absorb the residual ghcr/cache blips.
- A red leg is cosmetic: images are content-addressed, the prior `:latest` stays valid, the next main push self-heals. Don't chase it as a build break.

## pypistats.org throttling
pypistats `/api/packages/<pkg>/recent` 429s aggressively on unauthenticated bursts. Any script hitting it needs retry+backoff plus inter-request sleep (~1.5s). `scripts/suite_download_badges.py` is the reference implementation — preserves the prior badge value when throttled so the workflow exits 0.
