# Quality gates: the suggestion gym and zero-config quality at scale

The two scheduled gates that guard ER quality rather than correctness -- `bench-suggest-quality`'s gym and `bench-quality-scale`'s QIS -- and how to re-bless each.

## bench-suggest-quality gym-gate + gym baseline re-bless
`.github/workflows/bench-suggest-quality.yml` gates the config-suggestion kernel. On PUSH it runs only the fast `gate` (deterministic subset, ~min); the nightly `schedule` + `workflow_dispatch` ALSO run the heavy `gym-gate` (FULL_DIST catalog recovery vs `scripts/suggest_quality/baselines/gym_scorecard.json`, ~70–120 min). **A green push does NOT mean the gym-gate is green** — only the nightly exercises it, so it can sit red on `main` for days while every PR looks fine.
- **Re-bless after an intentional kernel change:** `gh workflow run bench-suggest-quality.yml --ref <branch> -f mode=gym-bless` regenerates `gym_scorecard.json` under FULL_DIST and commits it to the branch. That auto-commit carries `[skip ci]` (see the gotcha above), so if the PR then needs its own CI to go green, push a clean follow-up commit.
- **Degenerate-ceiling skip (#1620, 2026-07-10):** `gym.run_catalog` skips any dataset whose zero-config CEILING F1 is below `GOLDENMATCH_SUGGEST_GYM_CEILING_FLOOR` (default 0.50). `recovery_pct = (recovered−degraded)/(ceiling−degraded)` is meaningless when the ceiling is already broken: on `historical_50k` the WEIGHTED zero-config path reaches only F1 ~0.26, the damage gaps are tiny, and the raw diagnostic convergence (`verify=False`, no health net) blindly over-applies threshold moves — so a small F1 wiggle amplified into ±10x recovery that dragged the gated `headline_raw` to −1.28 and kept the nightly red. **f1_ceiling is the discriminator, NOT controller health** — every gym dataset commits a best-effort RED config (`confidence_required=False`), so synthetic/anchor hit F1 1.0 yet still log RED; well-behaved datasets sit at f1_ceiling 0.96–1.0. (The FS path fares far better on historical_50k, but the gym uses the weighted path.)
- **Degenerate-skip is now VISIBLE + ADVISORY in the gate (#1934 fix, 2026-07-21):** the skip previously did a bare `continue` and emitted NO record, so the gym-GATE couldn't tell a legitimate degenerate skip from an erroring/absent dataset — a blessed dataset that later drifts below the floor (`ncvr_synthetic` fell there between blesses: 50K, oversized clusters, RED config) re-failed every blessed pair as **MISSING** and the shrunken headline mean tripped `headline_raw`, *contradicting the skip's own intent*. Fix: `run_catalog` emits a dataset-level **skip sentinel** (`status="skipped_degenerate_ceiling"`); `_cmd_gym_gate` reports a blessed pair absent for THAT reason as **SKIPPED** (advisory `~`, non-gating), while absence for any OTHER reason stays **MISSING** (fail). Headlines now compare over the **COMMON measurable population** (built-rule pairs ok in BOTH baseline and this run) — recomputed from the baseline's per-pair `recovery_pct_*`, NOT the stored scalar — so a dataset leaving the set can't phantom-shift the mean, while a real drop on a still-measured dataset is fully caught (unit-tested). Net: a degenerate-drift no longer reds the nightly; re-bless is now optional cleanup (drops the SKIPPED pairs), not the only remedy. The underlying `ncvr_synthetic` ceiling degradation is a separate zero-config-quality question (not a suggestion-recovery regression), so it belongs to a QIS-style gate, not this one.

## Zero-config quality-at-scale gate (`bench-quality-scale.yml`, 2026-07-11)
The guard against the class of bug that sat broken at **≥500K rows for ~2 months**: zero-config ER quality (F1) was only ever *asserted* at ≤20K rows (autoconfig anchor gate `row_cap=20_000`, gym-gate ≤10K, Febrl3 ~5K), while zero-config decides everything from a **1,000-row sample** (`autoconfig.py`) and switches code paths at **50K** (learned blocking) and **100K** (controller refuse + planner rungs). The only harnesses that measured F1 at scale (`quality_invariant_scale.py`, `scale_audit_5m.py`, the ER head-to-head bench) were **all report-only + dispatch-only** — so a ≥500K regression was structurally below every gate that could fail, and `main-health` can't surface a report-only bench that never goes red.
- **`scripts/qis_gate.py`** turns the existing QIS harness (labeled, prefix-stable data + real F1 via `score_quality`) into a fail-on-regression gate. It runs TRUE zero-config `dedupe_df` (no config passed) across a matrix bracketing the thresholds (`ci` tier = 50K/100K/500K/1M; `heavy` = 5M) and fails on any of three checks: **scale-invariance** (a larger rung's F1 must not fall >`--scale-tol` below the smallest rung — needs NO historical baseline, catches the exact bug class), **baseline-delta** (vs committed `scripts/baselines/qis_scorecard.json`), **absolute-floor** (`--abs-floor`, default 0.80). Pure `evaluate_gate()` is unit-tested (`scripts/test_qis_gate.py`, no goldenmatch needed).
- **`dedupe_df` RAISES `ControllerNotConfidentError` at ≥100K when the config is RED** (the `REFUSE_AT_N=100_000` guard). `measure_rungs` catches it and **re-runs the committed config with `allow_red_config=True`** (+ `_skip_finalize=True`, the `run_rung` measurement idiom — `confidence_required=False` NO LONGER bypasses the RED-refuse post-#715, so it can't be used here) to MEASURE the F1, recording `refused=True` as context. **Pass/fail is on the measured F1, NOT the refuse verdict** — RED is a confidence flag (the corrupted-realistic shape excludes every exact-identity column → fuzzy-name-only blocking the confidence heuristic dislikes), and a RED config whose F1 still clears the floor + tracks the reference is NOT a quality regression. Only a rung whose F1 is genuinely UNMEASURABLE (the force-run skipped/errored — e.g. OOM-risk pair explosion) is recorded `f1=None` and auto-flagged (an honest can't-measure, never a fabricated 0.0). A real scale regression still surfaces as an F1 DROP (floor / scale-invariance). **(#1933 fix, 2026-07-21):** the earlier code recorded the refusal as `f1=None` unconditionally and auto-failed — a false positive on the heavy-tier 5M rung, whose RED config actually clusters at high F1 (100K measures F1 1.0; 5M refuses only because fuzzy-name blocking gets costly at scale). The docstring already promised the measure-and-decide-on-F1 behavior; the code now matches it.
- **Ships with NO committed baseline on purpose** — scale-invariance + absolute-floor work on day 1; the first `-f mode=bless` run in CI populates the scorecard to also enable drift detection. Bless in CI (native/version parity), never locally.
- **Schedule:** nightly `0 5 * * *` (ci tier, `large-new-64GB`) + weekly `0 6 * * 1` (heavy 5M). `main-health` (#1637) auto-surfaces a red within 6h; `scripts/qis_alert.sh` additionally files/updates a dedicated `quality-regression` issue assigned to `benzsevern` on a scheduled failure. Detection latency ~1 day vs the ~60 this cost. NOT in `ci-required` (scheduled watch, not a PR gate). Sets `ARROW_DEFAULT_MEMORY_POOL=system`.
