## Code Patterns
- **Cross-surface controller telemetry uses ONE serializer**: `goldenmatch.web.controller_telemetry.serialize_telemetry(profile, history, committed_config, source, run_name, recorded_at)`. Every v1.7-v1.12 surface (web `/api/v1/controller/telemetry`, TUI Controller tab, CLI `goldenmatch autoconfig`, REST `/autoconfig`, MCP `auto_configure` tool, A2A `autoconfig` skill, SQL `goldenmatch_autoconfig_telemetry()`, Rust bridge `autoconfig()`) delegates here. SQL bridge + DuckDB UDFs fall back to a minimal hand-rolled blob (`{available, source, stop_reason, health}`) when `goldenmatch[web]` extra isn't installed. Capture telemetry by reading `goldenmatch.core.autoconfig._LAST_CONTROLLER_RUN.get()` post-`auto_configure_df()` — returns `(profile, history)` or `None`.
- **Product analytics ≠ controller "telemetry" (2026-06-15):** `goldenmatch/core/analytics.py` is anonymous, **opt-in** usage analytics to PostHog (engagement signal PyPI downloads can't show) — a DIFFERENT thing from `web/controller_telemetry.py` (auto-config introspection returned to the caller, sends nothing anywhere). Don't conflate the two; the word "telemetry" stays reserved for the controller surface. **OFF unless `GOLDENMATCH_ANALYTICS=1` AND `POSTHOG_API_KEY` set** (owned hosted services — docs site via Mintlify `integrations.posthog` in `docs-site/docs.json`, Railway MCP deploy — set the flag server-side; user machines stay silent unless they opt in). **PII-free by construction:** `capture(event, props)` keeps only `_ALLOWED_PROPS` (coarse scalars — `scale_bucket(n)` bands, never exact counts; backend/version/os) and drops any path-like (`/`,`\`) or >64-char value; MCP capture sends the tool NAME only, never `arguments`. Fail-open (daemon-thread POST, 2s timeout, all errors swallowed; never blocks a run). Anonymous UUID4 at `~/.goldenmatch/analytics_id`. Hooks: `_api.py::_capture_run` (dedupe_df/match_df), `cli/main.py::_callback` (command name), `mcp/server.py::call_tool` (tool name). The privacy contract is TESTED in `tests/test_analytics.py` (default-off, allow-list, value rejection, fail-open) — a regression fails CI. Full collection list: `packages/python/goldenmatch/ANALYTICS.md`. Web-UI/TUI client-side (posthog-js) is a planned follow-up. Reads key from env — NEVER hardcode `phc_*`; `docs.json` carries a `phc_REPLACE_WITH_POSTHOG_PROJECT_KEY` placeholder.
- **Pydantic typed-accessor pattern for Optional invariants.** `MatchkeyConfig.threshold` / `MatchkeyField.scorer`/`weight`/`field` are typed Optional at the Pydantic level (YAML round-trip) but guaranteed non-None for `weighted`/`fuzzy` matchkey types post-validation. Pattern (PR #151): keep the field Optional, add a `@property` accessor (`fuzzy_threshold`, `fuzzy_scorer`, `fuzzy_weight`, `resolved_field`) that raises `ValueError` if the invariant was broken via post-construction mutation, and use the accessor at call sites that need the narrowed type. Pyright stops seeing Optional — dropped 7 `# pyright: ignore` suppressions in `scorer.py`.
- **Pre-flight config linter (`goldenmatch/core/config_lint/`, 2026-06-15).** Data-shape sanity checks on the RESOLVED config (zero-config OR explicit) — closes the gap that an explicit config bypasses every controller guard (only Pydantic + column-existence ran). **Registry is the single source of truth**: the same `LintRule` that the engine turns into a `Finding` also emits its `### {title}` section in the GENERATED `docs-site/goldenmatch/config-linter.mdx` (via `docgen.render_lint_docs`), so a finding's `rationale` == the documented reason — they cannot drift. `scripts/gen_lint_docs.py --write|--check` (the `--check` no-drift gate is also asserted in `tests/test_config_lint.py::test_docs_not_stale`; regenerate after touching `rules.py`). Rule thresholds are literals MIRRORING the auto-path constants (e.g. `_SIMPLE_PLAN_MAX_PAIRS`), pinned to source in `test_thresholds_tied_to_source_constants`. Engine is deterministic/offline/**fail-open** (a raising rule is skipped, never mutates config); NO network/LLM in the gate (that opt-in advisory layer is a planned follow-up). **Gate policy = warn-and-run, refuse opt-in**: `GOLDENMATCH_CONFIG_LINT` = `warn` (default: log + attach to `DedupeResult/MatchResult.lint_findings`, never block) / `strict` (raise `ConfigLintError` on an ERROR finding before the pipeline) / `off`. Wired in `_api.py::_run_config_lint` for `dedupe_df`/`match_df` only — file-based `dedupe()`/`match()`, CLI/TUI, and MCP/A2A exposure are follow-ups. All current rules are WARN, so `strict` never fires until an ERROR rule lands.
- **Pyright suppressions on multi-line imports.** `# pyright: ignore[reportMissingImports]` must sit on the `from X import (` line itself, NOT on the imported-symbol continuation line. Pyright reports the error at the `from X` column; a comment on a later line doesn't satisfy it. Bit us on `autoconfig_policy.py` (openai) and `scorer.py` (sentence_transformers) in PR #147.
- Auto-config exact matchkeys: `col_type in ("zip","geo")` NEVER backs an exact matchkey (blocking signal, not identity claim). Exact matchkeys require `cardinality_ratio >= 0.5`. Skipped columns still flow into `build_blocking()`.
- Auto-config learned blocking: gated at `total_rows >= 50_000` in `autoconfig.py`. Sample size capped at `min(total_rows // 4, 5000)` so learner has held-out rows. Below 50K, static/multi_pass is default.
- **Per-identifier blocking union (#1207 PR1, default-on):** when no single exact key clears the 0.20 `NULL_RATE_CEILING`, `build_blocking` emits a `multi_pass` union via `_build_strong_identifier_union` (one pass per strong-id col [identifier/email/phone] + `[first,last]` + name+geo), gated on union-level >=0.95 OR-coverage. Single-field strong-id passes use a NON-NULL scale gate (`_id_pass_scale_safe_nonnull`) because `blocker.py` filters null/sentinel single-field block keys before blocks form; compound/name passes keep the null-inclusive `_gate_passes`. #876 perfect-surrogate (card_ratio>=1.0) excluded. Recall 1.0 vs name-only 0.004 on planted dups. **>=50k reconciliation (#1316, RESOLVED):** `_legacy_auto_configure_v0` used to force `strategy="learned"` unconditionally at `total_rows >= 50_000`, OVERWRITING the union — so via the public entry point the union only took effect <50k rows. MEASURED: learned does NOT rediscover the union — on the null-sparse strong-id shape at 50k, candidate-pair recall collapses **1.0 (union) -> 0.0 (learned)** (the learner trains on a <=5k sample, finds no pairs above its 0.95 recall threshold, falls back to one column, and `skip_oversized` then drops every resulting giant block). The gate now KEEPS a strong-id union it detects (`_is_strong_identifier_union`: multi_pass + >=1 single strong-id pass) instead of overwriting it (the union's per-id blocks are near-unique/bounded, so learned's block-bounding value is redundant); learned stays the default for every non-union large shape. NOTE the force lives in `_legacy_auto_configure_v0` (the controller's v0 heuristic, invoked via `autoconfig_controller.py`) and only fires on the DETERMINISTIC/weighted path — the probabilistic (FS) routed path never reaches it. Tests: `tests/test_blocking_union_learned_1316.py`.
- `DedupeResult.total_records` = `dupes.height + unique.height` (golden is a rollup, NOT a separate row population). Adding golden double-counts every multi-member cluster.
- **`scored_pairs` is LAZY on the B2c FS path — read it via `core.pairs.materialize_scored_pairs(results)`, never `results.get("scored_pairs") or []` (#2417).** The pipeline no longer materializes the `list[tuple]`; on the B2c FS path (`_use_fs_columnar`) it sets `results["scored_pairs"] = None` and carries the deduped Arrow table under `results["scored_pairs_table"]`. **A bare `.get` therefore reads EMPTY — a silent wrong answer, which is exactly why the helper exists**; the four in-tree dict consumers (`web/preview.py`, `web/routers/run.py`, `cli/review.py`, and `_api.py`'s two `DedupeResult(...)` sites) all go through it. On the DATACLASS the accessor is a lazy property over `_scored_pairs_table` (same field→property idiom as `clusters`) that **caches a real `list`**, so `isinstance(r.scored_pairs, list)` (`test_api.py`) and `== []` (`test_fs_scored_pairs_shed_2006.py`) still hold — do NOT "simplify" this to a lazy sequence / `list` subclass, which would make `== []` read True until first access. WHY: MEASURED 168 B/pair resident (192 B/pair transient) for the Python list vs **24 B/pair** for the Arrow table (7x), and `GOLDENMATCH_FS_SCORED_PAIRS_MAX` defaults to 50,000,000 → the cap permitted an ~8.4 GB post-cluster allocation that the `dedupe_df` + identity path never reads (`resolve_clusters` takes `scored_pairs` for signature compatibility only and works off `pair_score_view`). Companion: `_finalize_review_pairs_arrow` does the linked-set anti-join in Arrow because the list version built `linked_keys` as a Python set over EVERY linked pair — a second O(pairs) driver structure. **That filter is NOT skippable** even though review/linked come from one threshold split: `score_buckets_arrow` can emit the same pair on several blocking passes with different scores and the dedup runs LATER, so a pair really can sit on both sides of the cut.
- Internal columns prefixed with `__` (e.g. `__row_id__`, `__source__`, `__mk_*__`)
- File specs are tuples: `(path, source_name)` or `(path, source_name, column_map)`
- `GoldenMatchConfig.get_matchkeys()` returns matchkeys from either top-level or match_settings
- Matchkey type field: use `mk.type` (not `mk.comparison`) after validation
- Scorer returns `list[tuple[int, int, float]]` — (row_id_a, row_id_b, score)
- Pair confidence IS the match score (0.0-1.0) — no separate confidence field
- `build_clusters` returns `dict[int, dict]` with keys: members, size, oversized, pair_scores, confidence, bottleneck_pair, cluster_quality
- `cluster_quality` field: `"strong"` (normal), `"weak"` (confidence downgraded), `"split"` (auto-split from oversized)
- `confidence` = 0.4*min_edge + 0.3*avg_edge + 0.3*connectivity; `bottleneck_pair` = weakest link (id_a, id_b)
- Oversized clusters are auto-split via MST (minimum spanning tree) — weakest MST edge removed to guarantee disconnection
- `unmerge_record(record_id, clusters)` removes a record from its cluster, re-clusters remaining via stored pair_scores
- `unmerge_cluster(cluster_id, clusters)` shatters a cluster into singletons
- TUI has 9 tabs: Data, Config, Matches, Golden, Boost, Export, Controller, Corrections, Suggestions (key 1-9)

- `match_one(record, df, mk)` in `core/match_one.py` — single-record matching primitive for streaming
- **CandidateStore (`core/candidate_store.py`, 2026-06-13):** pluggable per-probe candidate retrieval behind the ANN `match_one` path. `FrameCandidateStore` (default, in-RAM) gathers ONLY the top-K candidate rows — the refactor that replaced `_match_one_ann`'s per-probe `df.to_dicts()` over the whole base (O(N)/probe). `LanceCandidateStore` (opt-in, `pip install goldenmatch[lance]`) serves the same gathers from a Lance dataset on disk (random `take` + BTREE `block_key` scalar index) for an out-of-core base. `match_one(..., store=)` takes one; `build_base_store(df, path=, configured=)` builds it via `resolve_base_store_kind` (env `GOLDENMATCH_BASE_STORE` ∈ {`auto`,`memory`,`lance`}, default `auto` → lance only above ~2M rows AND lance importable). Env-only opt-in (no Pydantic field). **Measured (`scripts/bench_match_one_lance.py`, 10M skewed base): ANN-stream gather 3.6 ms/probe at 182 MB RSS (lance) vs 0.1 ms at 1233 MB (in-RAM) vs 240 ms (parquet, no random access) — ~7x less memory at streaming-fine latency.** Default path byte-identical (parity-gated, `tests/test_candidate_store.py`). Note: the brute `match_one` path and the streaming/incremental callers (which don't build an ANN index today) stay on the in-memory frame — Lance only helps the sparse ANN gather, not a full scan. **Validated on REAL NCVR (3M voters, `scripts/validate_lance_base_store_ncvr.py`, real char-ngram FAISS ANN): Frame vs Lance `match_one` byte-identical (50/50 real probes, 0 mismatches); ANN-stream gather 4.6 ms/probe @ 172 MB vs in-RAM 0.1 ms @ 708 MB (~4x less memory). Real exact-zip-block gathers favor the in-RAM filter (memory 4.2 ms vs lance 10.4 ms — NCVR zip blocks are large), so the win is the SPARSE ANN gather only. Verdict: default stays `memory`; lance opt-in confirmed, NO default flip.**

- LLM scorer: `llm_score_pairs()` in `core/llm_scorer.py` — accepts `LLMScorerConfig` with optional `BudgetConfig` for cost tracking, model tiering, and graceful degradation
- **Local LLM scorer throughput — CPU multiprocessing does NOT help (D3 investigated + rejected 2026-08-02):** `_local_score_pairs` (`provider="local"`, the in-process pinned 1.5B) scores the borderline band SEQUENTIALLY, and that's deliberate. Fanning the band across a spawn process pool (each worker its own llama.cpp context) was built + parity-verified but measured **0.34x — ~3x SLOWER** with 2 workers on a 4-core box, at both small (6) and amortized (20) band sizes. Root cause: llama.cpp CPU inference is **memory-bandwidth-bound and already saturates every core for a SINGLE inference**, so N workers just split the cores + thrash the memory bus + reload the model per worker. First-principles: on an already-core-saturating, bandwidth-bound workload, process parallelism can't add throughput. The real local-throughput levers are **GPU offload (`GOLDENMATCH_LOCAL_LLM_GPU_LAYERS`), a smaller/distilled model, or fewer LLM calls (tighter candidate band)** — NOT process parallelism. (The HOSTED path stays threaded — it's network-bound, a different regime.) The mp code was reverted; the finding is in the `_local_score_pairs` docstring so no one re-attempts it.
- **Local 1.5B scorer on product matching — the honest number is walmart_amazon 0.795 (beats DeepMatcher, BELOW Ditto), NOT "above SOTA" (CORRECTED 2026-08-02):** the pinned in-process 1.5B (`provider="local"`) is where the local-LLM value lives (the FS scoring/blocking levers on structured PII were all dead ends). **RETRACTION:** the earlier `bench_product_matching.py` "Amazon-Google F1 0.886, above DeepMatcher/Ditto" claim was **CONTAMINATED** — `amazon_google` is one of the 1.5B's SIX TRAINING sources (`scripts/er_matcher/sources.yaml`: bundle mechanism, not `eval_only` → `build_corpus.py:205` folds it into the training corpus, alongside abt_buy/dblp_acm/dblp_scholar/febrl/synthetic). Benchmarking on a training dataset measures memorization, not skill; 0.886 > Ditto 0.756 is the tell. The **only held-out, comparable number is walmart_amazon ZERO-SHOT F1 0.795** (walmart is NOT a training source), where DeepMatcher=0.669 (we beat it) and Ditto=0.868 (we are BELOW it — Ditto fine-tunes RoBERTa on each dataset's OWN train split; we can't match that zero-shot). So the defensible claim is **a competitive local/private/zero-config scorer** (beats classic baselines out of the box, no per-dataset training, no API) — NOT SOTA-beating. LESSON (again): a too-good number demands hunting the confound BEFORE trusting it — here, checking the training-set membership. `bench_product_matching.py` is retained as an IN-DISTRIBUTION sanity check ONLY (its docstring now says so); a valid product comparison must run on a HELD-OUT dataset (e.g. walmart) against the canonical DeepMatcher/Ditto test split.
- LLM budget: `core/llm_budget.py` — `BudgetTracker` class tracks token usage, cost, and enforces `max_cost_usd`/`max_calls` limits. Budget summary in `EngineStats.llm_cost`
- Fellegi-Sunter: `core/probabilistic.py` — EM-trained m/u probabilities, comparison vectors (2/3/N-level), match weights as log-likelihood ratios. New matchkey `type: probabilistic`
  - Splink-style EM: u estimated from random pairs (fixed), only m trained via EM. Blocking fields get fixed neutral priors
  - Continuous EM (`train_em_continuous`) available but not default — discrete levels are more stable
  - `ContinuousEMResult` + `score_probabilistic_continuous` for advanced users
  - **Vectorized block scoring (2026-06-07, default ON):** `score_probabilistic_vectorized` replaces the per-pair Python double loop with one `rapidfuzz.cdist` NxN matrix per field + numpy level/weight/normalize — the same path the fuzzy scorer uses (`core/scorer._fuzzy_score_matrix`). **9x faster** on full DBLP-ACM blocks (9.6s→1.06s, 1.2M pairs) at 99.96% pair parity (boundary-level differences within native-kernel/rapidfuzz tolerance, same as the legacy fast path). The pipeline picks it via `probabilistic_block_scorer(mk, em)`; falls back to scalar `score_probabilistic` for embedding/record_embedding scorers or `GOLDENMATCH_FS_VECTORIZED=0`. The continuous E-step (`train_em_continuous`) and `score_probabilistic_continuous` are also vectorized now. The old `probabilistic_fast.py` (per-pair indexed loop) stays for back-compat + its tests, but is no longer wired into the pipeline.
  - **Block-scoring perf — value-dedup + small-block batching (2026-06-12, PR #869, default ON, −72% on `historical_50k`):** the FS numpy path was per-block-fan-out bound, NOT compute bound — `historical_50k` makes 31,735 blocks, 79% ≤8 rows, ~222k tiny FFI-bound `score_field_matrix` calls. (1) `_field_score_matrix_dedup` scores the DISTINCT values per field and gathers via an index map — bit-identical EXCEPT exact/soundex (multiplicity-based) need the unique-matrix diagonal pinned to the self-score 1.0 (equal-value off-diagonal pairs read it). (2) `score_probabilistic_vectorized_batch` + `score_probabilistic_blocks_batched` coalesce small blocks (cap `GOLDENMATCH_FS_BATCH_ROWS`, default **256** — sweep knee; 512 was past it) into one S×S matrix per field, slice each block's DIAGONAL sub-matrix (off-diagonal cross-block cells discarded); native calls 222k→4.3k. Bench-dump path stays per-block; native-FS / scalar / model-backed fall back. **The native FS Rust kernel does NOT help here** — the wall is the per-block loop, not scoring math (the `gm_prob_native` bake-off column = numpy, no change). **Correctness gate = fixed-`em_result` PAIR-SET diff, NOT cluster count** (the pipeline is non-deterministic ±3 clusters run-to-run from EM-sample order). Decision: `context-network/decisions/0012-fs-block-scoring-perf.md`. Next lever (unmet): per-block `collect()` avoidance. **Candidate-pair dedup across passes was ATTEMPTED (PR #2295, `GOLDENMATCH_FS_PAIR_DEDUP`) and REVERTED** — it does not pay off and is a dead end. Three reasons found on re-audit: (1) it was SHADOWED on the default path — the default-on B2c columnar path (`_fs_columnar_cluster_enabled`) has the same eligibility and is checked first, so `score_fs_pair_dedup` got 0 calls on the common single-FS-matchkey zero-config route (its parity test was consequently a NO-OP); (2) it had a real correctness bug — it ignored `fs_missing_mode` (#1846), so on a `"disagree"` config (which `historical_50k` auto-configs to) it treated nulls as neutral not level-0-against → precision collapse 0.928→0.365; (3) even fixed + fully optimized (native batch value-pair scoring + progressive weight-bounded pruning) it is ~4× SLOWER and ~3× more RSS than the bucket/columnar route (68.5s vs 16.5s on `historical_50k`) because the scorers auto-config picks for person data (`ensemble`/`given_name_aliased_jw`/`name_freq_weighted_jw`) have NO native batch kernel, so pair-dedup Python-loops them while the bucket route uses native `score_field_matrix` batch + within-block value-dedup. The premise ("remove 1.86× cross-pass re-scoring") is weaker than it looks: the bucket route already value-dedups WITHIN block, so cross-pass re-scoring is bounded by distinct VALUES, not pairs. It could only win on a config using EXCLUSIVELY native-eligible scorers (jaro_winkler/levenshtein/token_sort/exact), which zero-config person data does not produce. Do NOT re-attempt without a native batch kernel for the composite scorers.
  - **FS native scoring reads precomputed `__xform_<sig>__` columns (2026-08-01, no flag, byte-identical) — the `bucket_score` −82% fix.** The native FS path (`_score_fs_native_frame` → `_fs_arrow_column` arrow / `_field_values_for_block` Vec) RE-APPLIED matchkey field transforms per-row in Python, ONCE PER BUCKET, even though `precompute_matchkey_transforms` already materialized the transformed values as `__xform_<sig>__` columns on the full frame (kept through `bucket_slim_projection`). `GOLDENMATCH_BUCKET_DEBUG=1` attributed **~90% of the `bucket_score` stage to this input-prep** (`row_ids`+`field_arrays` rebuild) vs **~4% actual Rust compute** — the #688/#869 orchestration-bound class, still alive on the FS path. Fix: both readers now PREFER the precomputed `__xform_<sig>__` column when present — the arrow path returns its buffer **ZERO-COPY** (skipping `.to_list()` + per-row `apply_transforms` + `pa.array` rebuild). This mirrors the WEIGHTED fast path, which already reads `_xform_sig(f)` (`score_buckets.py:950`); the FS path simply never got it. **Byte-identical by the precompute contract** (`__xform_<sig>__` == the `apply_transforms` fallback — the same equivalence the weighted path relies on); falls back to the raw field where the column is absent (paths that skip precompute). **MEASURED (1M realistic, clean non-debug A/B, 2 rounds): `bucket_score` 41.9s → 7.4s (−82%, ~5.6×), end-to-end wall −21% (~30s), cluster hash IDENTICAL (a2f5b09817 on branch AND main), peak RSS flat.** Helps EVERY FS run (not config-specific). Tests: `test_fs_bucket_native.py::test_fs_field_readers_prefer_precomputed_xform_column` (locks the precomputed-column preference + the raw-field fallback) + the existing byte-parity suite. Smaller un-done follow-ups found in the same dig: (1) the per-call **const rebuild** (`weights`/`scorer_ids`/`levels` rebuilt from `em_result` every bucket call) is hoistable; (2) `score_buckets` ran **twice** in the 1M trace (216k blocks then 100k) — a second scoring invocation worth understanding.
  - **FS EM block-slim projection (2026-07-20, `GOLDENMATCH_FS_EM_BLOCK_SLIM`, default ON; `=0` = full-width parity oracle):** the FS memory PEAK is NOT `score_buckets` — it's `build_blocks` for EM training. Measured (person 100K, `scripts/bench_fs_vmrss_probe.py`): VmRSS jumps 187→2084 MB **between `auto_configure` and EM**, entirely upstream of `score_buckets` (which the weighted path shares and peaks at only 467 MB — the two FS-specific costs the non-prob path skips are EM + its `build_blocks`). Root cause: EM reads ONLY the `__row_id__` column of the blocks it samples (`_sample_blocked_pairs_with_fields`; the sampled pairs' field values are looked up on the full `score_frame`, never the block frames), yet `build_blocks` materializes every block at FULL source width across every multi_pass/SN pass (56,935 blocks × ~5.6M row-materializations × 14 cols ≈ 1.67 GB at 100K person). Fix (`pipeline._build_em_blocks`): project the EM block-frame to `[__row_id__] + collect_blocking_fields(...)` before `build_blocks` — width 14→6, **build_blocks 1674→695 MB, whole-pipeline peak 2126→1114 MB (−48%), byte-identical output** (EM's row-id membership + per-block `blocking_fields` provenance unchanged; sig-verified on person + biblio). Complementary to `GOLDENMATCH_FS_EM_SAMPLE_ROWS` (that caps block COUNT above the row cap; this caps each block's WIDTH at every scale, incl. the ≤cap no-sample regime). GOTCHAs: (1) block frames materialize as **pyarrow Tables** — `Table.columns` is ChunkedArrays, names live on `.column_names` (a naive `col in native.columns` silently no-ops the projection → fell back to full width in the first cut). (2) `_build_em_blocks` must use the **module-level** `build_blocks` (line 21), not a local re-import — `test_probabilistic.TestModelReuseSkipsBuildBlocks` monkeypatches `pipeline.build_blocks` and a local import shadows the patch. (3) Scoped to the `_em_only_blocks` path (bucket route + trained EM, no bench dump) — the bench-dump/non-bucket branches read block row DATA, so they keep full width. Defensive fallback to full-width blocks if the projection can't cover a column `build_blocks` needs. - Sensitivity analysis: `core/sensitivity.py` — parameter sweep engine. `run_sensitivity()` varies threshold/blocking/matchkey params, compares each run against baseline via CCMS. `SweepParam`, `SweepPoint`, `SensitivityResult` with `stability_report()`. Per-point error handling preserves partial results.
- Domain extraction: `core/domain.py` — auto-detects product subdomain (electronics vs software), extracts brand/model/SKU/color/specs (electronics) or name/version/edition/platform (software). Model normalization strips hyphens, region/color suffixes. Pipeline step between standardize and matchkeys.
- LLM extraction: `core/llm_extract.py` — LLM-based feature extraction for low-confidence records. Reuses BudgetTracker. O(N) preprocessing, not O(N^2) pair scoring.
- Domain registry: `core/domain_registry.py` — YAML-based custom domain rulebooks. Search paths: `.goldenmatch/domains/` (local), `~/.goldenmatch/domains/` (global), `goldenmatch/domains/` (built-in). MCP tools: `list_domains`, `create_domain`, `test_domain`
- MCP `suggest_config` tool: analyze bad merges, identify guilty fields, suggest threshold/weight changes
- REST review queue: `GET /reviews` returns borderline pairs for steward review, `POST /reviews/decide` records approve/reject decisions
- **Wave 3.3 (2026-06-05): REST matching server (`api/server.py`) gained cluster surgery.** `POST /shatter {cluster_id}` (break a cluster into singletons, mirrors the MCP `shatter_cluster` tool) and `POST /unmerge {record_id, threshold?}` (pull a record out of its cluster) — both call `MatchServer.shatter_cluster`/`unmerge_record_op`, which delegate to `engine.unmerge_cluster`/`unmerge_record` and update `self.result`. Auth-gated by the Wave 1 `_authorized()` check. Audit note: web shatter was ALREADY covered (`POST /api/v1/runs/{name}/unmerge` with `mode="cluster"`), and web evaluation derives ground truth from steward **labels** (browser-writable via `POST /api/v1/labels`), NOT a server-local GT path — so those two audit "gaps" were already closed; only the REST server lacked cluster surgery.
- Daemon mode: `watch_daemon()` in `db/watch.py` — adds health endpoint (HTTP /health), PID file, SIGTERM handling to watch mode
- PPRL package: `pprl/protocol.py` — multi-party privacy-preserving record linkage. `PPRLConfig` dataclass, `run_pprl()` convenience function, `link_trusted_third_party()` and `link_smc()` protocol implementations. CLI: `goldenmatch pprl link`. Bloom filter security levels (standard/high/paranoid) with HMAC salting and balanced padding in `utils/transforms.py`.
- Ray backend: `backends/ray_backend.py` -- distributed block scoring via Ray tasks. Drop-in replacement for ThreadPoolExecutor. `pip install goldenmatch[ray]`, config `backend: ray` or CLI `--backend ray`. Auto-initializes locally, falls back to parallel scorer for <= 4 blocks. Pipeline uses `_get_block_scorer(config)` to select scorer function.
- PPRL auto-config: `auto_configure_pprl()` profiles data and picks optimal fields, bloom filter parameters, and threshold. Beats manual tuning -- 92.4% F1 on FEBRL4 (vs 89.8% manual), 76.1% F1 on NCVR. MCP tools: `pprl_auto_config`, `pprl_link`.
- LLM clustering: `core/llm_cluster.py` — in-context block clustering as alternative to pairwise LLM scoring. Config `llm_scorer.mode: cluster`. Builds connected components from borderline pairs, sends blocks to LLM, synthesizes pair_scores from cluster confidence for compatibility with Union-Find/unmerge/lineage. Degrades: cluster → pairwise → stop.
- Evaluation: `core/evaluate.py` — `EvalResult` dataclass, `evaluate_pairs()`, `evaluate_clusters()`, `load_ground_truth_csv()`. CLI: `goldenmatch evaluate --config X --ground-truth Y`
- Incremental CLI: `cli/incremental.py` — match new CSV records against existing base dataset. Handles exact (Polars join) and fuzzy (match_one brute-force) matchkeys separately
- Domain packs: 7 built-in YAML rulebooks in `goldenmatch/domains/` — electronics, software, healthcare, financial, real_estate, people, retail. Auto-discovered by `discover_rulebooks()`
- GitHub infrastructure: `.devcontainer/` (Codespaces)
- dbt integration: top-level `packages/dbt/goldensuite/` package with `run_goldenmatch_dedupe()` for DuckDB tables
- Python API: `_api.py` provides `dedupe()`, `match()`, `dedupe_df()`, `match_df()`, `pprl_link()`, `evaluate()`, `score_strings()`, `score_pair_df()`, `explain_pair_df()` convenience functions. `__init__.py` re-exports ~101 symbols. `DedupeResult`/`MatchResult` have `_repr_html_()` for Jupyter.
- REST client: `client.py` — `Client(base_url)` with `.match()`, `.list_clusters()`, `.explain()`, `.reviews()`. Uses stdlib `urllib` only.
- CI/CD quality gates: `goldenmatch evaluate --min-f1 0.90 --min-precision 0.80` exits code 1 if thresholds not met
- Pipeline backend selection: `_get_block_scorer(config)` in pipeline.py returns `score_blocks_parallel` or `score_blocks_ray` based on `config.backend`
- PPRL vectorized similarity: use numpy matrix multiply (`mat_a @ mat_b.T`) for bloom filter dice, NOT per-pair Python loops. 13x speedup.
- PPRL auto-config: penalize near-unique fields (IDs), long fields (>15 chars), high-null fields. Min threshold 0.85. max_fields=4 beats 6.
- NCVR voter data: tab-delimited, 488MB zip at `tests/benchmarks/datasets/NCVR/`. Gitignored. `birth_year` only (no full DOB). `ssn` is Y/N flag not actual SSN. The 10K-row sample at `ncvoter_sample_10k.txt` is the file the controller benchmark consumes; created by streaming the first 10K rows out of `ncvoter_Statewide.zip` (avoids the full 4.3GB extract). Both files are gitignored.
