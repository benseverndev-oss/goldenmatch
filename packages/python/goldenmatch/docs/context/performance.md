## Performance
- Exact matching uses Polars self-join (not Python group_by + combinations)
- Fuzzy matching uses `rapidfuzz.process.cdist` for vectorized NxN scoring
- Fuzzy blocks scored in parallel via `ThreadPoolExecutor` (`score_blocks_parallel` in scorer.py)
  - rapidfuzz.cdist releases the GIL so threads give real parallelism
  - Blocks are independent — frozen `exclude_pairs` snapshot avoids races
  - For <=2 blocks, skips thread overhead and runs sequentially
  - All call sites (pipeline.py, engine.py, chunked.py) use the shared helper
- Intra-field early termination in `find_fuzzy_matches`: after each expensive field, breaks early if no pair can reach threshold
- Standardizers have native Polars fast path (`_NATIVE_STANDARDIZERS` in standardize.py)
- Matchkey transforms have native Polars fast path (`_try_native_chain` in matchkey.py)
- Clustering uses iterative Union-Find (not recursive) with lazy pair_scores
- Blocking key choice dominates fuzzy performance — coarse keys create huge blocks
- 1M exact dedupe: ~7.8s. 100K fuzzy (name+zip): ~12.8s via pipeline
- Scale curve: 7,823 rec/s at 100K records on laptop (fuzzy + exact + golden)
- 1M records (scale-audit Round 3, 2026-05-11, `polars-direct`): ~43 min wall on a GitHub `ubuntu-latest` (4-core, 16 GB) runner, 9.98 GB peak RSS, 836K clusters, no OOM. Roughly split half auto_configure + half run_dedupe. Default (Linux, tracemalloc off) fits comfortably in 16 GB through 1M.
- **5M records (scale-audit 2026-05-14, `chunked` + `explicit-personlike`, PRs #233/#234/#235):** ~50 min wall on `ubuntu-latest` (4c/16GB), 11.9 GB peak RSS, 618,817 multi-member clusters, no OOM. Bottleneck is wall, not memory. Prior chunked impl had O(N²) cross-chunk Python loops + eager `pl.read_csv` materialization; B (PR #233) vectorized cross-chunk via Polars join, C (#234) added per-block bucketed index so pure-index blocks are never instantiated, D (#235) wired `config.backend="duckdb"` to actually do something (pair store out-of-core; doesn't help 5M-on-16GB but lands real implementation for >50M tier).
- **5M with `backend="duckdb-backend"` (D smoke):** still OOMs on 16 GB — expected. D moves pair *storage* out-of-core but the in-memory polars-direct pipeline is unchanged, so block scoring matrices still hit the ceiling.
- **Recommended for 5M today:** `backend="chunked"` + `config_mode="explicit-personlike"` when you want the call to *succeed* on synthetic-surname-shape fixtures (the same pathology, with the same shape, that motivates explicit-personlike — see also `docs/superpowers/specs/2026-05-15-controller-v3-planner-design.md` for the v3 backend planner that picks chunked automatically when iteration *does* succeed). Controller-budget v1 (2026-05-16, PRs #271-#276) closed the silent-degenerate-dedupe gap: at `df.height >= 100_000`, when sample iteration commits a RED config, `auto_configure_df` now raises `ControllerNotConfidentError` instead of running a 26-min noise-result dedupe. Adaptive sample size (sqrt-scaled, capped at 20K) + 60-120s budget at 100K+ rows ALSO makes iteration succeed more often on real-shape data. Callers who want today's warn-and-run can pass `confidence_required=False`.
- **`ControllerNotConfidentError` semantics (2026-05-16, PRs #271-#276):** Raised by `auto_configure_df` / `dedupe_df` / `match_df` when (a) `confidence_required=True` (default), (b) `df.height >= 100_000`, AND (c) the controller's committed `ComplexityProfile` is RED. Fields: `n_rows`, `failing_sub_profile` ∈ {`data`, `blocking`, `scoring`, `matchkey`, `cluster`}, `stop_reason` (StopReason name). Recovery options: pass an explicit `GoldenMatchConfig`, lower the matchkey threshold, or opt out with `confidence_required=False`. Adaptive budget table: `<5K -> 15s/full`, `5K-100K -> 30s/2K (historical)`, `100K-1M -> 60s/sqrt(n)*20 capped at 20K`, `>=1M -> 120s/20K`. Source: `core/autoconfig_controller.py:REFUSE_AT_N` + `ControllerBudget.for_dataset`. Spec: `docs/superpowers/specs/2026-05-16-controller-budget-vs-blocking-discovery-design.md`.
- **Controller v3 planner (2026-05-16, PRs #259-#266):** 7 rules over `(ComplexityProfile, RuntimeProfile)` pick `ExecutionPlan(backend, chunk_size, max_workers, pair_spill_threshold, clustering_strategy, rule_name)`. Rules: user_override (first, beats all), pathological, simple (< 100K rows, < 50M pairs), fast_box (>= 32GB RAM), chunked (50M–5B pairs), ray (>= 50M rows + ray installed), duckdb (>= 5B pairs OR < 16GB RAM). Plan stored on `RunHistory.execution_plan` and surfaced on PostflightReport.__str__, web telemetry, CLI panel, and MCP responses (single `serialize_telemetry` serializer). 100K zero-config wall = 21.14s median on `large-new-64GB` (gate ≤ 24s, PASS).

- **Benchmark harness (2026-05-15, `core/bench.py`):** stage timing + pair-count accounting. Zero cost when no recorder is pushed; capture via `with bench_capture() as rec: ...`. Pipeline wraps `auto_configure`, `exact_matching`, `fuzzy_scoring` (with `fuzzy_build_blocks` + `fuzzy_score_blocks` inner stages), `cluster`, `golden`, `identity_resolve`. Metrics include `record_count`, `block_count`, `block_size_p50/p95/p99/max`, `exact_pair_count`, `fuzzy_pair_count`, `scored_pair_count`, `cluster_count`, `multi_member_cluster_count`, `oversized_cluster_count`. `scripts/scale_audit_5m.py` reads `bench.to_dict()` and dumps it into the report's `pipeline_bench` field + markdown summary. Tests: `tests/test_bench.py`.
- **Golden-record build vectorized (2026-05-15):** the per-cluster `collected_df.filter(__row_id__.is_in(member_ids))` loop in `_run_dedupe_pipeline` was O(N·K) work — bench harness surfaced it at 36% of wall on an 11K-row run. New shape: one filter to multi-member rows, one `replace_strict` to attach `__cluster_id__`, then `partition_by("__cluster_id__")` and iterate per-partition. Empirical: golden stage dropped from 1.255s → 0.135s (9.3x) on a 1116-multi-member-cluster synthetic. At 5M with ~600K multi-member clusters the lift is the difference between "the dominant stage" and "rounding error." Tests: `tests/test_golden_partition_perf.py` lock the output equivalence (one golden per multi-member cluster, no cross-cluster value bleed, oversized still excluded).
- **DuckDB backend was 5x slower than polars-direct (2026-05-15):** `score_blocks_duckdb` was single-threaded AND used `con.executemany("INSERT ...", rows)` which costs ~1ms per row at scale — 90K pairs took 104s. Two fixes: (a) `ThreadPoolExecutor(max_workers=4)` for parallel block scoring, mirroring `score_blocks_parallel`; (b) bulk INSERT via DuckDB's Arrow integration (`pa.table(...)` registered as a local-named view, `INSERT INTO ... SELECT * FROM arrow_table`). Empirical: 100K zero-config audit 129s → 24.4s (5.3x). The Arrow bulk-load fix moves INSERT from 104s to 0.098s — 1060x faster on that step alone. The `arrow_table` local name is load-bearing for DuckDB's zero-copy view resolution; flagged with `# noqa: F841`.
- **Bench harness thread-safety lessons (2026-05-15):** the recorder's `add_timing`/`set_metric` are now lock-protected (`threading.Lock`) so worker threads in `score_blocks_parallel` can't corrupt totals via lost dict updates. Do NOT wrap `with stage(...)` inside per-block / per-pair hot loops running under threads — even with the lock, GIL contention from `time.perf_counter()` + dict write pairs serializes workers with rapidfuzz's GIL release and slows the whole pipeline. Pipeline-level stages (single main-thread writer) are fine; per-scorer wraps in `find_fuzzy_matches` are NOT.

- **`bucket_score` 44x slowdown on 8-core EPYC Linux (issue #688, fixed 2026-06-03, PR #692, `goldenmatch-native 0.1.3`):** the native block kernel's internal rayon `par_iter().collect()` parked the calling thread on a `LockLatch` futex with near-zero progress (~190s wall, ZERO scoring CPU via py-spy `--native`). **Env-specific** -- reproduces only on `ubuntu-latest-xlarge` (8c AMD EPYC 9V74), NOT `large-new-64GB` (16c) or `ubuntu-latest` (both sub-second), so any bucket-backend perf claim must name the runner. The kernel's rayon path was parity-validated but never perf-validated on Linux (the 25M bench above predates the arrow kernel #514). Fix: kernel scores in the CALLING thread below `GOLDENMATCH_NATIVE_RAYON_MIN_PAIRS` (default 20M pairs/call) and only fans out to rayon above it; the Python `score_buckets` already parallelizes across buckets so nothing is lost. Verified 286.9s -> 1.2s (240x) on the wedge runner, byte-identical output. Diagnose `bucket_score` substep splits with `GOLDENMATCH_BUCKET_DEBUG=1` (prep vs kernel vs post-filter). A secondary, non-load-bearing bug (stale 0.1.0 wheel missing `build_exclude_set`) is in the root CLAUDE.md `goldenmatch-native` section. Memory: `project_688_stale_native_wheel`.
- **Bucket fast-path vectorized lane (2026-06-12, `score_buckets._score_block_vec`, default-on `GOLDENMATCH_BUCKET_VEC_MIN=32`/`VEC_MAX=2000`):** the fast-path Python per-pair fallback (`_score_one_bucket_fast`, the branch reached when the planner picks `bucket` but the scorer is NOT native -- `soundex_match` is the common case, since native-on makes the planner pick `bucket` while soundex_match has no native kernel id) is a triple-nested Python double loop whose interpreter overhead dominates (pyinstrument: the loop body is the cost, the scorer call doesn't even surface). The lane replaces it, for blocks in `[VEC_MIN, VEC_MAX]`, with one batched **float64** `cdist` / matrix per field (`_vec_field_matrix`) + numpy threshold scan; only emitted pairs touch Python. **float64 NOT float32** -- `_fuzzy_score_matrix`'s float32 would flip borderline `>= threshold` decisions, so the lane is bit-identical to the per-pair loop (asserted scorer-by-scorer in `tests/test_score_buckets_vectorized_fallback.py`; `_VEC_SUPPORTED` = {soundex_match, jaro_winkler, levenshtein, token_sort}). **dice/jaccard are EXCLUDED** -- their `_dice_score_matrix`/`_jaccard_score_matrix` are the PPRL bloom-filter (hex) scorers, a different computation from the per-pair bigram callables (the parity test catches it: `bytes.fromhex` raises on plain strings). **Measured (`scripts/bench_lowscale.py`, this box): per-block 2.3x at n=50, 3.8x at n=1000; but END-TO-END on the realistic_person soundex shape only ~5-7% because low-scale blocks are mostly tiny (<32) and the lane correctly leaves those on the per-pair loop.** vec_min=32 is the Pareto-safe floor: the end-to-end cross-over sweep breaks even at ~16, is net-positive by 32, and the lane REGRESSES ~1.5x if forced onto tiny blocks (numpy alloc/triu overhead) -- so 32 never makes a workload slower while capturing the big-block win. **This is a large-block scoring win, NOT a low-scale win**: iteration-1 profiling confirmed the low-scale wall lives in clustering (build_cluster_frames/union-find ~39% at 40K) + `auto_configure`, not per-pair scoring. Gated off entirely with `GOLDENMATCH_BUCKET_VEC_MIN=1000000000` (byte-identical to the old per-pair path). NE present / nulls in a field column / non-supported scorer all fall back to the per-pair loop.

- **Blocking-aware shuffle scoring (#844, opt-in, `GOLDENMATCH_DISTRIBUTED_BLOCK_SHUFFLE=1`, default OFF):** the Phase-5 distributed scorer (`distributed/scoring.py::score_blocks_distributed`) scored each ARBITRARY input partition in isolation (`read_parquet_partitioned` does a plain `ds.repartition(n)`, NOT keyed by any blocking column), so two true duplicates were compared only if they happened to land in the same partition. Recall scaled inversely with `n_partitions` (issue #844 measured 10.68M multi-member clusters at 1024 partitions vs 52.16M at 256 on the same 346M input). NOTE the headline "all output singletons" in #844 was a MISREAD: golden emits one row per `__cluster_id__` by construction, so unique-id-per-row is tautological, and ~335M singletons were correctly dropped. The opt-in path explodes each record to `(record, __keyid__, __block_key__)` rows (one per blocking pass via `_build_block_key_expr` + one per exact matchkey value), `repartition(keys=["__keyid__","__block_key__"])` to co-locate block-mates regardless of input partition, then scores within each group with `batch_size=None` (the legacy path also lacked the `batch_size=None` that `local_cc_assignments` uses). Default branch is `_score_blocks_legacy`, byte-identical. **Kept opt-in because the shuffle makes pairs cross input-partition boundaries, so `local_cc_assignments` is no longer sufficient and clustering needs a real distributed WCC** (`two_phase_wcc` collects to driver and wedges the head at 100M; `distributed_wcc` pointer-jumping avoids the collect but can deadlock Ray's streaming executor at scale). That WCC-at-scale question gates flipping the default + wiring it into `_run_phase5_pipeline`. Tests: `tests/test_distributed_block_shuffle.py` (no Ray; reproduces the cross-partition miss + the fix on the real kernel).
